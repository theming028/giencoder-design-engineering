## ★★★ 本日双坑（已写进两份 PLAYBOOK / MEMORY）

### 坑一：`core.autocrlf = true`

`git status` 冒出 **10 页 ` M`**、每页 `wc -c` 比 `git cat-file -s HEAD:…` 大几百~几千字节 ⇒ 像被改坏。
**根因**：仓库 blob 存 **LF**、工作区落盘 **CRLF** ⇒ 天然差「**行数**」个字节，**不是内容改动**。

### 坑二：★ 口径算错（本会话最大坑）

**`len(bytes) − CRLF数` 不是字符数**（本页中文极多，一个汉字 3 个 UTF-8 字节 ⇒ 虚高约 **6.8 万**）。
我一度用它当「字符数」，把 `860993 → 865762` 写进 acceptance / HANDOFF，直到 `apply106.py` 自己打印 `796243 → 797333` 才发觉对不上。

**正确判据** = **先归一化行尾、再比同一口径**：

```python
ws = io.open(p,'rb').read().decode('utf-8').replace('\r\n','\n')
hd = subprocess.run(['git','cat-file','blob','HEAD:'+p],capture_output=True).stdout.decode('utf-8')
len(ws) - len(hd)     # 真·内容增减（Unicode 字符口径）
```

**同一份文件三种数**：Unicode 字符 **797333**（第三拍前）/ **798613**（终态）｜ UTF-8 字节(归一) **869581** ｜ 工作区字节(CRLF) **874274**。

⇒ 教训：**「页面字节数」这类历史记录必须注明口径**；`wc -c` / `cat-file -s`（原始字节）与 `git diff`（规范化内容）是两套口径，别混用。

## ★★★ 本日第三条教训：用户只给**一个数**时，反查那个数、别按类名字面改

邵先生原话只有「**宽度是固定的 728px**」，而他第 4 条点名的类却是 `.r93-wrap` —— **两者不是同一个东西**。
⇒ **数字比类名可信**（类名靠记忆、数字是他现场读到的）：「**数字 → 元素**」反查（**全页宽扫描 + 全仓 grep 那个字面值**）
比「**类名 → 直接改**」安全一个数量级；**反查过程本身就是证据链**（能解释「为什么不是他说的那个类」）。
⚠ 连带两件事：① 用户**不重开窗口**说「还是没解决」时，先怀疑「改的东西在他那个分辨率下看不见」（本条 1440 就是不可见）；
② **改动在用户点名的分辨率下不可见时，必须在汇报里明说 + 给出「哪里才看得见」**。
