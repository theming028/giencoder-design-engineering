## Affix box-shadow 改造为 1px 硬线（应用第一性 + 对抗式审查）

- 需求：.yuanqi-affix 的 box-shadow 改造为"像一根 1px 线条一样的效果"。
- 第一性：box-shadow 模拟 1px 线 = 0 模糊 + 1px 长度 + 颜色 + 0 偏移（贴合元素边缘）。但 Affix 吸顶方向是**底边**为分界线（不是顶边），所以 inset 用 `-1px`（y=-1，贴底）而非 `1px`（y=+1，贴顶）。
- 对抗式审查：现状 `.yuanqi-affix` **同时有** `border-bottom: 1px solid` + `box-shadow: var(--shadow1-down)`，两个一起做"线"与"投影"——**双层视觉冗余**！border 已经画了 1px 实线，shadow 又做雾化扩散，合起来视觉是"模糊雾里找一条线"，与用户期望的清晰 1px 硬线不符。
- 修复方案：去掉 border-bottom 1px（避免双线），box-shadow 改为 `inset 0 -1px 0 var(--color-border-1, #eaedf1)` —— 与 Table 分页器同款 pattern（0 模糊 + 1px 高度 + 贴边 + 与 border 同色 → 视觉融合成清晰硬线）。
- 顺手改预览页第 57 行说明文字：从"底部细分隔线 + 轻微投影"改为"底边 1px 硬线（box-shadow: inset 0 -1px 0 模拟）"，避免文档与实现脱节。
- puppeteer 验证：boxShadow = `rgb(242, 243, 245) 0px -1px 0px 0px inset`（与 --color-border-1 同色），borderBottomWidth = 0px，视觉确认工具栏底边一条清晰的 1px 硬线。
- 提交 `033a6f6`：2 files / +4 / -4，推送成功（远端 ls-remote 确认 = 033a6f6）。
- 副作用：本次推送遭遇 GitHub 502 + 坚果云持续生成 .lock 双重干扰，但最终 033a6f6 实际已上远端，只是本地 `origin/main` ref 缓存因 lock 干扰没更新。下次类似情况：以 `git ls-remote origin main` 为准判断推送真伪，不要被本地 ref 缓存误导。
- 教训：
  1. **border + box-shadow 不要同时做"线"和"投影"**，职责重叠会模糊视觉。要么纯 border、要么用 inset shadow 模拟 1px 线，二选一。
  2. **Affix 吸顶要看清方向**：`inset 0 -1px 0`（底边硬线，吸顶后底部分界）≠ `inset 0 1px 0`（顶边硬线，例如 Table 分页器在底部要的是顶边）。方向反了就成"投影在另一侧"的错觉。

## 2026-09-10 16:05 — gray 色阶按 OKLCH 感知均匀色彩空间重设计

**任务：** 用户说"最浅灰色是 #F3F4F5，按国际色彩标准重新设计"。

**关键判断：**
- "国际色彩标准" = CSS Color 4 / CIE 224-2:2015 / Björn Ottosson 2020 的 **OKLCH** 感知均匀色彩空间
- 比简单 RGB 等差更接近人眼感知（Material Design 3 / Apple HIG 现行标准）
- 手写 OKLab 算法（sRGB→linear→LMS→OKLab→OKLCH），无需色彩库依赖

**OKLCH 计算：**
- 起点 #F3F4F5 → L=0.9667, C=0.0017, H=247.84°（C 极小接近中性，H 微蓝）
- 末档 L=0.18（对应 #111212，避免纯黑失去层次）
- 等 ΔL=0.0874 阶梯 10 阶

**生成色阶：**
gray-1 #F3F4F5 → gray-10 #111212，每档 B 通道比 R/G 高 1（起点色相印记，肉眼不可见）

**验证（puppeteer + OKLab 反向）：**
- 渲染端实测 = 计算值完全一致（量化误差 0）
- 9 档 ΔL 实测 0.0854~0.0891（设计 0.0874，±2%）
- ΔE(OKLab) ≈ ΔL（chroma 极小），感知均匀性达成

**教训：**
1. **"国际色彩标准"在设计系统语境中默认指 OKLCH**——不要再用 HSL/HSV（不感知均匀）或 CIELAB（旧标准，OKLCH 更准确）
2. **OKLCH 等 ΔL 阶梯 vs RGB 等差阶梯**：浅色端差异最大。RGB 阶梯的 #F7F7F7→#F2F2F2→#E5E5E5 前两档肉眼几乎一样，OKLCH 不会有这问题
3. **双主题共享同一 L 值基底**：亮色/暗色只是方向相反，不重新生成色阶，避免亮色均匀切暗色不均匀
4. **暗色 bg 单独 L 阶梯**（不和 gray-1..10 复用），bg-1 通常比 gray-1 更深（近黑）
5. **起点色相会渗透整条色阶**——起点 #F3F4F5 有 1 个 B 偏色，10 阶每档都带这个印记；如需严格 R=G=B 把 RGB 三值改相同即可

**教训（重要）：**
1. **OKLCH 等 ΔL 在浅色端会被"拉宽"**——设计系统用 OKLCH 时灰阶起点 L 通常 0.95-0.97，

3. **"国际标准"不是死的**——CSS Color 4 允许非等 ΔL 阶梯（如 gamma 2.2 perceptual），如需浅色
