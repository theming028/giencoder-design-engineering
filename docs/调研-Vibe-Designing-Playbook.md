## 二、这本书回答的核心问题

开篇立论：**AI 并非不懂设计，而是它的创造力被「分布收敛」（toward-average 的倾向）掩盖了。**

- 需求含糊时，模型会收敛到训练数据里最高频、最稳妥的结果——统一无衬线、浅色背景配紫色渐变、四平八稳的布局。通用、安全，也因此平庸。
- 真正的问题不在模型不强，而在于它缺少「向专业判断靠近」的机制。
- 结论：**设计师要做的，不是等更聪明的模型，而是把专业判断明确建立起来、注入给它，并沉淀为机制稳定产出。**

贯穿全书的核心判断：**能把「什么是好」讲清楚的，始终是人**。模型能学会执行、复用、规模化地应用判断，但判断本身要先由一个真正懂设计的人立起来。

## 三、三章主线（一条连续的逻辑线）

| 章 | 主题 | 解决什么 |
| :-- | :-- | :-- |
| **01** | 设计工程 · Design Engineering | 把「什么是好」写成 Agent 能读取的**声明（声明标准）与契约（执行路径）**，让生成从碰运气变成可控，稳定接近明确质量标准。 |
| **02** | 动态交互 · Dynamic Interaction | 界面不再预先画死，而是随用户**真实意图**在运行时生成——先想清任务，再决定此刻该出现什么。 |
| **03** | 自我进化 · Self-Evolution | 让产物被持续评估、被打回重做，在 **taste** 牵引下不断突破模型的设计能力上限。 |

三章对应设计进入 AI 生成系统的三个位置：**生成前的可控性 → 运行中的适配 → 生成后的改进**。

## 四、第一章：设计工程（核心概念）

### 4.1 Design I/O —— 生成链路拆解
不把生成当黑盒，而是拆成一道道可介入、可检查、可回流的「接口」工序：

- **主链路**：需求 → 理解规划 → 搭骨架 → 填充 → 细化 → 产出原型 → 末端评估。
- **token 注入**：颜色/间距/字号等约束非单一工序所有，自搭骨架起贯穿全局（视觉一致性靠「每一步都不破坏既有约束」）。
- **critique 回流**：评估不达标不必从头来，带着具体问题退回规划或相关环节。

设计对象首先不是静态页面，而是**信息如何被组织、暴露和验证**。

### 4.2 设计声明 vs 执行契约
作者强调这两类不是先验设计出来的，而是**从一次次生成失败里整理出来的**两类系统性缺口：

> **声明管方向，契约管路径。**

| | 设计声明 | 执行契约 |
| :-- | :-- | :-- |
| 回答问题 | 什么样的设计是好的 | 怎么把它做出来 |
| 来源 | 生成结果反复错在同一类判断上 | 标准写了，但链路里没人调用 |
| 典型内容 | spec、domain、craft、design.md、components、template | skill、evaluator |
| 缺失后果 | 产物能跑，但判断失准 | 标准很多，但进不了流程 |

**六份设计声明**（对应六类反复出现的生成缺陷）：

| 生成暴露的问题 | 声明 | 约束什么 |
| :-- | :-- | :-- |
| 主流程能跑，空态/错误态/权限态消失 | `spec.md` | 功能定义、状态流、边界、验收标准 |
| 页面像通用 SaaS，不像云安全/数据库/控制台 | `domain.md` | 领域语义、风险编码、业务操作边界 |
| 功能完整，但一眼是 AI 模板 | `craft.md` | 排版、层级、动效、材质等通用工艺 |
| 色值、字号、圆角、动效散落代码 | `design.md` | token、视觉语义、状态派生、系统缺口 |
| 组件看起来像，但语义用错 | `components` | 组件可用范围和语义边界 |
| 页面骨架从零猜，场景结构走偏 | `template` | 页面骨架、app shell、场景结构起点 |

**两份执行契约**：`skill`（知道何时该读哪份声明、怎么用、做完怎么检查）与 `evaluator`（负责评估回流）。

### 4.3 实操：从一句话到一个页面
`ux-spec` skill 把一句话需求展开成六层框架（L1-L6），典型链路：
1. **理解/规划**：→ 产出 `spec.md`；同时确定 `design.md` 视觉规格（避免模型用默认视觉补位并带入后续）。
2. **信息架构设计**：`cloudai-picker` 从模板库选骨架（总览区/主任务列表/状态筛选/侧栏/操作区）；`variant` skill 可围绕同一 spec 生成多种 IA 方案（总览优先 / 任务列表优先 / 异常处理优先）。
3. **组件设计**：把信息映射到正确组件语义（状态 Badge / 风险 RiskBadge / 资源 Tag 不能混用），敏感字段默认脱敏。
4. **交互与状态设计**：补齐加载、空态、失败、重试、权限等边界反馈。
5. **视觉规格落地**：依赖 `design.md` + 设计词典，防止顺着默认 token 走下去。
6. **验收与回流**：参照 `evaluator` 标准自检，不达标回流重做。

关键提示：**「运行中」「高危」「ECS」「生产环境」都是短文本，但责任不同** —— 有的是状态、有的是风险、有的是资源类型、有的是环境标记。混成同一种标签，页面整齐但判断变慢。

## 五、第二章：动态交互（UX → AX → GenUI → A2UI）

### 5.1 从 UX 到 AX（Agent Experience）
- UX 帮用户在已经画好的界面（导航/表单/按钮/反馈）中把目标转成操作动作。
- AX 处理的是 Agent 能够**代用户行动**之后的新形态：用户先表达意图，Agent 理解目标、补齐上下文、推进任务，再把过程和结果交还用户判断。
- 引 John Maeda：*UX made complex systems usable... AX removes the journey altogether, teleporting people directly to their goals.*
- **执行鸿沟被压缩后，评估鸿沟会被放大**：用户没亲手做每一步，因此更需要知道 Agent 做了什么、为什么、哪里不确定、能否撤销修正。

> 关键洞察：**信息呈现的透明度并非越高越好**。把 Agent 规划/执行/总结的所有中间信息平铺给用户，透明度本身会变成新的信息负担。应根据**任务阶段、风险等级、用户决策需要**动态调节暴露的信息层级（参考文献：CSCW 2025 关于 AI 设计 Agent 过程透明度的研究）。

UX 与 AX 不是替代关系：稳定仪表盘、设置页、重复审批流仍应预设计成页面；AX Loop 适合有上下文、下一步依赖数据或推理、用户不一定知道准确路径但仍要负责的任务。

### 5.2 GenUI：新的 Interface（Generative UI）
- GenUI 是让**界面参与 Agent 系统运行**：根据意图、上下文、任务状态动态组织屏幕上该出现的内容、结构和判断点。
- **不是让模型自由写 HTML/CSS**，而是**受控生成**：Agent 输出结构化意图/界面描述，客户端用组件目录、渲染规则、交互约束来组织界面。
- 边界判断两维度：**表达自由度**（能做多复杂的内容）× **产品控制权**（最终界面由谁决定）。越自由，一致性与安全越难保证——**GenUI 追求有边界的灵活，不是无限自由**。
- 引入前自检查：任务路径/结果结构是否随上下文变化？用户是否需过程判断？结构化界面是否比长文本更好？能否被组件目录和规则约束？

### 5.3 A2UI：对话 Loop 中的动态机制
A2UI = **Agent to UI**，GenUI 的一种实现机制，本质是 **Agent 与客户端之间的契约**：Agent 声明「要表达什么」，客户端负责「如何渲染」。

契约通常调动四类资源：**业务数据**（指标/字段/实例/SQL/报告）· **工作流**（任务状态/下一步动作/是否暂停）· **组件**（允许渲染的 UI 模板）· **交互规则**（决策/超时/校验/风险确认/动作分发）。

核心分工示例（A2UI 消息示意）：Agent 只声明 `intent / status / title / context / content / actions / behavior`，而**不决定按钮长什么样、卡片用什么颜色、图表如何排版**。价值在于：把「要表达什么」与「如何渲染」分开，让 Agent 参与界面组织但不接管界面实现。

### 5.4 案例：OmniBox → FlexCard → GenReport
一条真实数据运营分析链路，三段式承接 AX Loop：
1. **OmniBox 承接意图表达**：把自然语言、数据范围、知识库、指标对象、历史上下文放同一入口，做**意图结构化**。
2. **FlexCard 承接过程协作**：承接中间判断点（方向选择、高权限 SQL 查询授权等），结构化卡片 + 风险提示 + 「用户确认前暂停执行」规则，用 A2UI 渲染。
3. **GenReport 承接结果评估**：复杂结果沉淀为可阅读、可分享、可继续追踪的 **Artifacts 交付物**，仍属 GenUI，靠声明式规则约束（指标必须出现、图表绑定数据、洞察引用证据）。

## 六、第三章：自我进化（从人工指正到评审运行时）

### 6.1 基调
**生成器 + 评估器** 双角色闭环。自我进化不是 AI 自己宣布自己变好了，而是把「人工指正」里那些**稳定判断**（第一屏看不出主任务 / CTA 与目标不一致 / 卡片节奏太平均 / 像一个通用模板...）写成可运行的评审循环。

- 生成器：把输入（需求 + spec/skills/components/design.md 等设计资产）变成原型 —— «提出第一版方案的人»。
- 评估器：像审稿人一样判断这版原型**能否进入下一步**，不达标准输出**可执行的优化指令**（不是「再优化一下」，而是「哪些判断没成立、证据在哪、下一轮先改什么」）。

### 6.2 评估标准：页面类型 + 六维度模型
先判**页面类型**（决定「用哪把尺子」），再套**同一组六维度模型**，不同类型仅权重不同：

- 页面类型三类任务：**转化型**（Brand Landing）、**任务型**（Product Console / Conversational）、**判断型**（Data Dashboard / Content Doc）。

**六维度评分模型**（从三类真实业务关注拆出）：

| 层级 | 维度 | 评审关注 |
| :-- | :-- | :-- |
| 业务语义层 | **Product Intent 产品意图** | 价值主张、目标用户、主任务、内容语气、CTA 是否匹配 |
| 业务语义层 | **Trust & Domain Fit 业务可信** | 领域术语、数据声明、风险权限、合规、AI 置信与证据 |
| 用户任务层 | **Information Architecture 信息架构** | 层级、分组、导航顺序、密度 |
| 用户任务层 | **Interaction Readiness 交互就绪** | 控件、状态、反馈、恢复路径 |
| 界面实现层 | **System Craft 系统工艺** | 组件、间距、字体、圆角、状态一致性 |
| 界面实现层 | **Visual & Brand Expression 视觉品牌** | 视觉层级、品牌记忆、表达一致 |

无任务时，prepare 阶段从 Web artifact（title/h1/导航/文案/图片/结构）**推断临时目标**，来源标记为 `inferred_from_artifact`。

### 6.3 证据链：让 AI 像人一样评估
关键主张：**evaluator 是一套完整的评估运行时，不是「让模型看 HTML 打分的提示词」**。评审的是交付物，不是生成器的意图。

四层证据（生产入口 `Evaluator/harness/design_review_cli.mjs`）：
1. **DOM/CSS QA**：横向溢出、文字裁切、低对比度、fixed 溢出、小点击目标、缺名称、图片损坏。
2. **Page Profile**：section、图片、链接、真实/占位路径、导航、CTA。
3. **Click Smoke**：点击可见目标后是否出现 console error / page error / broken image / dialog / 无反馈。
4. **Screenshot**：桌面（默认视口 1440×1000）+ full-page 截图。

设计要点：
- 运行时阻断外部字体依赖，减少截图判断的偶然性。
- **浏览器 QA 是事实层，不是评分层**——能确定溢出/断图/点击报错，但不能判断「有没有品牌记忆」。
- 评审边界明确为 **desktop-only**（明确不因缺移动端截图扣分），避免证据之外乱扣。

### 6.4 交付闸门：从分数到放行判断
**平均分会掩盖致命问题**，所以不只看分数，更看**放行判断**。三类信息收束：结构化评分 + 产物成熟度 + 阻断问题。

三种**评审模式**（改放行策略，不改评分模型）：

| 模式 | 阶段 | 阈值 | 重点 |
| :-- | :-- | :--: | :-- |
| `vibe_draft` 过程稿评审 | 方向探索 | 7.5 | 留探索弹性，后端/路由/占位链接多为提示 |
| `prototype` 原型评审 | 路径演示 | 8.0 | 主路径需可见模拟状态，交互问题影响通过 |
| `release_gate` 上线门禁 | 交付验收 | 8.0 | 要求生产化路径，占位路径可能阻断 |

**阻断问题（blocking findings）** 列表核心十余项，防止被均分抹平：`unclear_primary_task`、`critical_rendering_failure`、`broken_key_task_path`、`disconnected_controls_or_states`、`broken_conversation_flow`、`untrustworthy_ai_response`、`generic_template_output`、`inconsistent_design_system`、`subcheck_evidence_missing`、`screenshot_review_missing` 等。

### 6.5 工程化与标准维护
- **隔离系统保护评审对象**：评估器只读外显材料（任务/原型/截图/QA/评分模型/权重/上一轮结果），**不读**生成器内部材料（隐藏规划、私有推理、作者解释、无关历史）。评审看的是稿件，不是作者脑中的稿件。
- **报告契约五层**：放行结论、六维度评分、证据解释、阻断问题、优化指令；报告**中文优先**。
- **标准在运行时之外持续校准**：靠好/坏/混合/边界/品类五类案例复盘，回答「是否减少误放行、是否造成新误退回、是否过度惩罚某类页面」。
- 完整闭环：**生成 → 评估 → 回流 → 维护**。

## 七、方法论亮点 / 可借鉴点

1. **「声明 vs 契约」二分法很有实操价值**：声明（什么是好）和契约（怎么执行）职责分离，定位了文档为什么写了却不生效的根本原因。
2. **从失败反推能力**：六份声明不是先验设计，而是「一次次撞见失败 → 沉淀成系统性能力」。《结语》点题：设计判断从「停在设计师脑子里」变成「能被引用、被执行、被追责的系统能力」。
3. **证据链设计克制**：明确「浏览器 QA 是事实层、模型评审是解释层、运行时是落分层」，三者不可互替；评审只看交付物、不看意图。
4. **放行逻辑 > 分数逻辑**：用页面类型 + 六维度 + 评审模式 + 阻断问题，解决「平均分掩盖致命问题」的通病。
5. **受控生成**原则：GenUI/A2UI 坚持「客户端的组件目录 + 设计 token + 交互规则」兜底，Agent 只声明意图不接管渲染——正好呼应对抗「AI 味/分布收敛」的主张。
6. **中文原生 + 报告可复盘**：评估报告面向协作，正文讲「过程稿评审」而非内部字段名，强调「能被读懂才有机会被执行」。

## 八、对这个设计系统工作区的关联

本项目与你工作区（GienCoderDesignSystem，含 GienCoder-DESIGN.md 设计系统与 design-io 架构素材）高度相关，可直接借鉴：

- **把设计系统沉淀成 Agent 可读取的声明 + 契约**：`tokens → design.md / components → skill / evaluator` 的递进关系，可作为设计系统「AI 可消费化」的架构模板。
- **六维度评估模型可移植**：Product Intent / Trust & Domain Fit / IA / Interaction Readiness / System Craft / Visual & Brand 六维，可作为一种机制化的「代码/界面审查 rubric」落地到团队的 code-review 与设计走查。
- **页面类型权重思想**：同一系统服务不同类型页面（落地页/控制台/看板）时，同一套标准按类型调权，避免「用错尺子」。
- **证据链式走查**：跨界面试 PDF 往往是静态稿；参考其「真实打开页面 + DOM/视觉/点击三层证据」的做法，可提升走查的可靠性与可追溯性。
- **放行闸门与反馈回路**：把「打分」升级为「放行判断 + 优化指令 + 回流」，可作为设计交付/测试验收流程的参考范式。
