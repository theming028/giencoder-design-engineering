CHAPTER 01 · 设计工程
可控的高质量生成
3 节

核心：把一项设计任务「从一句话到一版原型」的黑盒，拆成一条可在每个环节注入能力的链路。目标 = 让 AI 产出符合你的规范，而不是只生成一张「看起来是个页面」的截图。

1.1 Design I/O

黑盒 → 链路。理解规划 → 搭骨架 → 填充 → 细化 → 评估。两条贯穿线：token 注入、critique 回流。

1.2 声明与契约

六份设计声明（定义"什么算对"）+ 两份执行契约（定义"怎么做"）。声明管方向，契约管路径。

1.3 Skill 封装调度

把能沉淀的判断封装成 skill，在链路对的位置自动挂载。实操：一句话 → spec → 页面 → 评估。

「设计，是为达成某个特定目的、对各要素所做的编排方案。」

Design is a plan for arranging elements ... —— Charles Eames

1.2 设计声明与执行契约
section 1.2

实践中反复撞见的问题沉淀成两类能力：声明回答「什么样的设计是好的」，契约回答「怎么把它做出来」。二者互补，不是并列清单。

设计声明 Design Declarations执行契约 Execution Contracts
回答问题什么样的设计是好的怎么把它做出来
来源生成结果反复错在同一类判断上标准写了，但链路里没人调用
典型内容spec · domain · craft · design.md · components · templateskill · evaluator
缺失后果产物能跑，但判断失准标准很多，但进不了流程

六份声明（都回答：什么算对）

  • spec.md：功能定义 — 状态流 / 边界 / 验收
  • domain.md：领域语义 — 业务对象 → 视觉编码
  • craft.md：通用工艺 — 挡住「AI 味」
  • design.md：视觉契约 — token 单一事实源
  • components：组件注册表 — 语义边界
  • template：页面骨架 — 场景结构起点

两份契约（都回答：怎么做）

  • skill：把能力封装成可被调度的单元
  • template：从验证过的结构起点出发，而非每次空白
  • evaluator：把「坏味道」判据抽象成可打分的标尺

少了声明不知好坏；少了契约无法落地。配齐才是一套完整能力。

CHAPTER 01 · 设计工程
spec.md：功能成立的六层定义
L1 → L6

规格驱动开发（SDD, Spec-Driven Development，OpenAI Sean Grove「The New Code」）：规格是人与 Agent 共同引用的唯一事实源，代码只是规格在某一次实现里的投影。

L1 定位与意图一句话定义 · 目标用户 · 场景清单 · 非目标
L2 信息架构空间区域划分 · 内容生长规则
L3 核心链路状态流转路径
L4 组件功能细节每个组件具体怎么表现
L5 边界条件空 · 加载 · 错误 · 权限不足
L6 验收标准满足哪些条件才算做对

关键要点

  • 边界清楚：spec 只定义功能成立条件，视觉交给 craft/design.md，组件选型交给 components。
  • 没写=不存在：模型的言外之意不补。没有写的状态、边界、验收标准，最后只能「差不多」。
  • 一句话需求 → ux-spec skill 展开成完整六层 spec。

行为边界声明（L1 三档自主权）

  • 始终：如自动保存草稿
  • 询问后：如发送数据到第三方
  • 永不：如重定向到可疑链接

缺它 → Agent 或过度殷勤（到处"你确定吗"），或在敏感操作上擅自行动。

加载态分档 与 领域语义
L5 · domain.md

加载态分档（不是所有等待都需要安抚）

  • <300ms：不展示加载，避免闪烁
  • 300ms – 2s：骨架屏，稳定布局
  • >2s：Loader + 进度说明
  • >10s：超时提示 + 重试入口

domain.md — 领域语义

把业务数据和状态正确编码成视觉。云产品里「运行中 / 高危 / ECS / 生产环境」责任不同，混成同一种标签会导致页面整齐但判断变慢。缺它 → 套"换个品类也成立"的通用皮 + 系统割裂（不再信任任何颜色）。

「土气测试」：把为某产品做的插画放到卖咖啡页面仍成立 → 只是通用"高级皮"，直接压分。

CHAPTER 01 · 设计工程
craft.md：通用工艺，挡住「AI 味」
Anti-AI-taste

机械化预检（确定性判据 → FAIL）

  • uppercase eyebrow 标签：数 section 顶部的大写标签数，超过 section 总数的 1/3 直接 FAIL。「九个 eyebrow 是模板，三个才是有意为之。」
  • 字体：默认禁用被 AI 滥用的 serif；换项目须换字体组。

动效：每个动画都要被动机驱动

解释「层级 / 反馈 / 状态变化」；「看起来很酷」不允许。「三个有意义的动画，好过三十个无意义的闪烁。」

常见 AI 痕迹（点名清单）

  • 混装的 serif 字体
  • 每个标题都挂 uppercase eyebrow 标签
  • 等大白卡、无层级网格泛滥
  • 蓝紫渐变卡片（缺乏品牌记忆）
  • 无意义的动效堆砌

判据与 evaluator 同源 —— 同一套「坏味道」标准贯穿生成与评审。

1.3 Skill：能力的封装与调度
section 1.3

现实问题：知识写下来 ≠ 会被用上。Agent 不知道它存在、不知道何时该读，就形同不存在。

① 触发条件

写在 description，列出触发信号。把调用时机也封装进去。

② 能力主体

固话一套原本靠经验的工作流（判断步骤）。

③ 分层引用

主文件讲流程，庞大细节放 references 按需读取。按需加载 = 控制信息进入视野的时机与量。

④ 沉淀的坑

原则 + 已知陷阱，对应一次真实犯错，写进 skill 替所有人记住。这是最"贵"的部分。

调度 —— 让 skill 在对的环节自动挂载

规划design-research · ux-spec · visual-spec

CHAPTER 02 · 动态交互
体验随意图被实时组织
4 节

核心：用户带着的是「意图」而不是「任务」。界面不再预先画死，而是围绕上下文和任务状态实时组织 —— 先想清任务，再决定此刻该出现什么。

2.1 UX → AX

Agent Experience：压缩执行鸿沟，处理放大的评估鸿沟。过程透明度按阶段 / 风险 / 决策需要动态调节。

2.2 GenUI

有边界的灵活性。受控生成：Agent 输出结构化意图，客户端用组件目录 / 规则渲染。

2.3 A2UI

Agent 与客户端的契约，结构化 UI 描述 → 受控组件渲染。2.4 案例：OmniBox → FlexCard → GenReport。

「UX 让路径更顺畅；AX 直接移除路径，把用户送到目标。」

—— John Maeda, Design in Tech Report
CHAPTER 02 · 动态交互
2.1 从 UX 到 AX
section 2.1

UX（仍有效）

  • 帮用户把目标翻译成系统操作：导航 / 表单 / 反馈
  • 适合：稳定的仪表盘、设置页、审批流
  • 执行鸿沟：有目标但不知如何转成系统动作

AX（Agent Experience）

  • 用户先表达意图，Agent 理解目标、补上下文、推进任务
  • 界面承接意图表达、过程协作、证据解释、结果评估
  • 评估鸿沟：用户没亲手做每步 → 更需要知道做了什么 / 为什么 / 哪里不确定 / 能否撤销

UX / AX 对照

设计对象用户如何操作界面用户如何委托、验证、修正 Agent 行动
主要挑战降低认知与操作成本压缩执行鸿沟 · 处理放大的评估鸿沟
界面职责入口 / 路径 / 控件 / 反馈意图表达 · 过程协作 · 证据解释 · 结果评估
典型形态页面 / 菜单 / 表单 / 按钮输入入口 · 动态交互卡片 · 生成产物

关键原则：过程透明度并非越高越好。Agent 产生大量中间信息，全平铺会变成新的信息负担 —— 应根据任务阶段 / 风险等级 / 决策需要动态调节界面暴露的信息层级。

CHAPTER 02 · 动态交互
2.2 GenUI：有边界的灵活性
section 2.2

GenUI 不是「自由生成页面」

  • 定义：让界面参与 Agent 系统的运行 —— 根据意图 / 上下文 / 任务状态，动态组织该出现的内容、结构、判断点。
  • 出现在哪：对话流 · 工作区 · 原生界面 · 生成后结果产物。
  • 判断标准：能否在运行时把任务状态转成可理解、可操作、可评估的界面。

边界要清楚

只在任务路径、判断依据、用户决策点变化的地方引入 GenUI；稳定页面（仪表盘 / 设置页 / 审批流 / 长期 IA）不必为「生成」而重新生成。

两个判断维度

  • 表达自由度 vs 产品控制权 —— 并非越自由越好。
受控生成（推荐）Agent 输出结构化意图 / 描述
↓
客户端渲染组件目录 · 渲染规则 · 交互约束

保留运行时组织能力，又让产品控制视觉质量、交互边界、安全风险。

引入前自检：任务路径是否随上下文变化？用户是否需过程判断 / 确认 / 修正？结构化界面是否比长文本更好懂？能否被组件目录和规则约束？

CHAPTER 02 · 动态交互
2.3 A2UI：对话 Loop 中的动态机制
section 2.3

A2UI（Agent to UI）：Agent 用结构化方式声明界面意图，客户端用受控组件、设计系统与交互规则完成渲染。本质是 Agent 与客户端之间的契约 —— 把「要表达什么」和「如何渲染」分开。契约的作用是定义边界。

① 业务数据

指标 · 表字段 · 实例状态 · SQL 计划 · 生成资产 · 报告

② 工作流

任务状态 · 下一步动作 · Agent 是否暂停

③ 组件

客户端允许渲染的 UI 模板

④ 交互规则

决策策略 · 超时 · 校验 · 风险确认 · 动作分发

分工方式（重点不是字段名）

  • Agent 不决定按钮长相、卡片颜色、图表排版
  • 只说明：任务状态 · 展示数据 · 可行动作 · 是否阻塞执行
  • 客户端据此选组件、按设计系统渲染
  • 用户点击后，客户端带上下文把动作传回 Agent —— 界面把用户判断重新写回任务上下文

FlexCard：CloudAI 的落地 —— Agent 只描述意图 / 内容 / 动作 / 行为约束，渲染层映射到组件 / token / 无障碍 / 降级。

// A2UI 消息（简化示意）
{
  "intent": "confirm", "status": "pending",
  "title": "确认是否继续分析",
  "context": {
    "object": "业务对象/id",
    "time_range": "最近 24 小时",
    "finding": "发现 3 个异常项"
  },
  "content": { "type": "options", "items": [
    { "id": "item_1", "label": "选项 A",
      "description": "影响范围最高/优先" },
    { "id": "item_2", "label": "选项 B",
      "description": "调用上升/继续观察" }
  ]},
  "actions": [
    { "id": "analyze_selected", "label": "分析选中项", "primary": true },
    { "id": "view_all", "label": "查看全部" }
  ],
  "behavior": { "requires_user_decision": true,
                "blocks_agent_execution": true }
}

2.4 案例：OmniBox → FlexCard → GenReport
section 2.4

典型 Agentic 云产品链路：OmniBox 承接意图，FlexCard 承接过程协作，GenReport 承接结果评估。

OmniBox意图输入
→
FlexCard过程协作
→
GenReport结果评估

OmniBox · 意图结构化

把自然语言、数据范围、知识库、指标对象、历史上下文放进同一入口。识别任务对象 / 分析维度 / 时间范围 / 权限边界 / 业务线索 → 转成 Agent 可推理上下文。

例："基于海外业务 3 月数据生成运营月报…"

FlexCard · 过程协作

承接中间判断 —— 分析方向选择（产业/品牌/门店）、高权限 SQL 查询授权、可能影响数据库性能的查询。把「不确定的是什么 / 可选路径 / 会访问什么数据或风险」放同一张结构化卡片。

GenReport · 结果评估

复杂结果的 Artifacts 产物。不是固定模板，也不是 A2UI 卡片放大版 —— 结构 / 重点 / 证据随目标与数据状态变化，但被声明式规则约束（哪些指标必须出现、图表如何绑数据、洞察引用哪些证据）。

一份可用 GenReport 回答 4 问

① 关键指标表现如何？② 哪些结构性问题 / 风险值得关注？③ 证据来自哪些图表 / 明细 / 对比？④ 建议动作和后续跟踪方式是什么？

不是所有页面都要生成：要识别哪些时刻会因意图 / 上下文 / 数据 / 决策变化而需要动态界面。

CHAPTER 03 · 自我进化
从人工指正到评审运行时
5 节

核心：自我进化 ≠ AI 自夸变好，而是把「稳定判断」变成一套可运行的评审循环，不断沉淀、回流、校准。

3.1 人工指正的尽头

稳定判断应被沉淀。两个角色：生成器（提出版本）+ 评估器（审查版本）。基础闭环 4 环节。

3.2 评估标准

先判断页面类型，再用同一组六维度模型评估，仅权重不同。subcheck 让分数可追账。

3.3–3.5 证据链 / 闸门 / 工程化

多模态证据运行时 · 交付闸门与停止规则 · 隔离系统 + 离线标准维护。

「AI 不是因为多跑几轮就会变好。它需要一套会看、会判、会回流、会校准的系统。」

CHAPTER 03 · 自我进化
3.1 人工指正的尽头
section 3.1

为什么要沉淀稳定判断

很多指正是重复的：「第一屏看不出主任务」「CTA 与真实目标不一致」「卡片节奏太平均」「像通用模板」「指标缺来源/时间窗」「按钮点了没反馈」—— 这些话在不同项目里反复出现。它们不是灵感，是稳定判断。稳定判断应该被沉淀。

两个基本角色

  • 生成器：把输入变成原型（自然语言需求 + Spec/Skills/component.md/design.md）。「提出第一版方案的人」。
  • 评估器：判断能否进入下一步。不生成方案、不主观打分，像审稿人 —— 只看当前原型 + 评审标准。
① 生成原型基于设计输入
→
② 评估判别按评审维度
达标?
✓ 输出进入最终设计
↩ 优化指令证据位置 + 影响维度 + 下轮方向

这不是取消人，是人的位置上移：不再每轮循环纠错，而是修订 framework / prompt / schema / harness policy，把稳定判断写成运行时能执行的契约。分数只是外显结果，证据链 + 回流路径才是价值。

3.3 证据链：浏览器、截图与检查项
section 3.3

Evaluator ≠ 「让模型看段 HTML 再打分」，而是多模态证据运行时：先收集证据 → 交给评审模型 → 运行时重算分数、处理阻断、生成报告。评审看的是稿件，不是生成器的意图。

DOM / CSS QA

横向溢出 · 文字裁切 · 低对比度 · fixed 溢出 · 小点击目标 · 交互元素缺名称 · 图片损坏

Page Profile

section · 图片 · 链接 · 真实路径 · 占位链接 · 导航 · headline · CTA · 可点击目标

Click Smoke

点击后是否有 console error · page error · broken image · dialog · 无反馈

Screenshot

桌面 1440×1000 + full-page，供 visual review 与报告引用

浏览器 QA 是事实层，不是评分层

能抓溢出 / 断图 / 太小 / 点击报错，但不能判品牌记忆、链路安心感。无 critical QA 仍可能很弱：首屏无读点 / 模块像模板 / 图表无诊断 / 点击无状态。浏览器把问题变事实，模型解释影响，运行时收束分数。三者不可互相替代。

截图补上 DOM 看不到的问题

DOM 完整 ≠ 用户看到的页面成立。当 DOM/CSS 检查与截图冲突时，截图证据优先（用户看的是画面）。五类截图判断：

  • text_readability 文字真实可读
  • visual_hierarchy 主次 / 阅读路径
  • composition_risk 遮挡 / 空洞 / 节奏
  • brand_tone_fit 品牌与品类
  • motion_purpose 动效服务目标

3.4 交付闸门：从分数到放行判断
section 3.4

为什么不能只输出分数：平均分会掩盖致命问题。闸门回答的不是「几分」，而是「能不能进入下一步」。

评审模式阶段阈值交互与集成策略
过程稿 vibe_draft方向探索7.5先看方向 / 意图 / IA / 品牌 / 工艺；后端、路由、占位链接多为提示
原型 prototype路径演示8.0不要求真实后端，但主路径需可见模拟状态；交互问题影响通过
上线门禁 release_gate交付验收8.0要求生产化路径 / 导航 / 数据 / 关键状态；占位路径可能阻断

优化指令 = 压缩（不是愿望清单）

❌ 继续优化视觉、增强交互、丰富内容。

✅ 第一屏价值主张被产品图遮挡，影响 Product Intent 与 Visual & Brand；先调标题层级 / 图文关系 / CTA 位置。

「为什么不能过」被翻译成下一轮能执行的工作。

停止规则保护循环（能停也是能力）

  • 达阈值且无阻断 → 通过
  • 达最大轮数 → 停止
  • 连续多轮标准差小且最佳分提升有限 → 平台期
  • 修订导致分数明显下降 → 返回之前的更好版本

自我进化不是无限迭代，而是在证据显示已通过 / 平台期 / 走偏时做可解释的停止判断。

CHAPTER 03 · 自我进化
3.5 工程化与标准维护
section 3.5

隔离系统保护评审对象

  • 可读（外显）：任务目标 · 页面原型 · 截图 · QA · 交互路径 · 六维度模型 · 权重 · 上轮结果
  • 不可读（内部）：生成器提示词 · 隐藏规划 · 私有推理 · 作者解释 · 无关历史

生成器计划了完整链路但页面只有占位按钮 → 按占位按钮处理；说"后续接真实数据"但当前无路径/状态/反馈 → 仍记为证据。

报告契约（五层，进入协作）

  1. 放行结论：分数 · 阈值 · 模式 · 通过/退回原因
  2. 六维度正式评分
  3. 证据解释：截图 / 结构 / 点击 / 运行 / QA
  4. 阻断问题：为何不能放行
  5. 优化指令：下轮问题 + 证据 + 影响维度

刻意把「评分」与「证据解释」分开；报告中文优先（说"原型评审"而非内部字段）。

标准在运行时之外维护

  • 好案例：保护标准别过严
  • 坏案例：检查阻断问题能否识别
  • 混合案例：局部出色但主路径失败 → 校准平均分与放行关系
  • 边界案例：接近阈值 → 看权重/检查项稳定性
  • 品类案例：美妆 / 金融 / 云产品 / 文档 / 控制台 → 校准同维度在不同品类的表现

「标准不是一次写完的。标准是在案例里长出来的。」

每次标准更新答 4 问

  1. 是否减少误放行？
  2. 是否造成新的误退回？
  3. 是否过度惩罚某类页面？
  4. 是否只修好一个样本却伤害了其他样本？

评审五步 + 回流索引
checklist

评审展开前先建立尺子

  1. 判断页面类型（转化 / 任务 / 判断）→ 选对应权重表
  2. 用六维度模型逐维评审，每维拆 subcheck、记 evidence / deduction / recommendation，聚合出分（可反推）
  3. 结合评审模式（draft 7.5 / prototype 8.0 / release 8.0）+ 阻断问题做放行判断（分数 vs 能否通过是两件事）
  4. 通过 → 输出；未通过 → 输出压缩的优化指令（问题 + 证据 + 影响维度 + 下轮方向），回流
  5. 运行时之外：用好 / 坏 / 混合 / 边界 / 品类案例持续校准标准

CLOSING · 结语

把「什么是好」
讲清楚

三章不是三套分散能力，而是一条连续的工作方式：第一章解决生成前可控性，第二章解决运行中适配，第三章解决生成后改进 —— 让每一版都留下经验。

AI 时代设计师最重要的位置：不是退到旁边看模型生成，也不是把专业压成一句更聪明的 prompt，而是把「判断」本身交给系统 —— 什么值得突出、什么必须克制、什么状态不能缺席、什么表达会伤害信任、什么样的结果才算完成。

「真正值得投入的，不是让 AI 看起来更像设计师，而是让它持续靠近我们定义过的好。定义「好」的人，仍然决定设计的边界。」
