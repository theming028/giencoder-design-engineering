# Vibe Design Playbook 深度整理

> 来源：https://alibaba-cloud-design.github.io/vibe-designing-playbook/
> 目的：把「什么是好的设计」从设计师直觉，变成 Agent 能读取、执行、评估、回流并持续进化的系统能力。
> 适用：日常 AI 生成页面的设计与评审任务。

---

## 总纲：一句话

**设计不是靠更聪明的 prompt 凭空生成，而是把设计师的判断拆开、写清、放进链路里：先定义「什么算对」（声明），再给出「怎么做」（契约），让 Agent 沿链路生成，由 evaluator 检查回流，再用真实案例持续校准标准。**

全书的组织是一条三层递进的「能力进系统」主线：

1. **第一章 · 设计工程** —— 生成前的可控性：声明 + 契约。
2. **第二章 · 动态交互** —— 运行中的适配：DUX → AX，实时组织界面。
3. **第三章 · 自我进化** —— 生成后的改进：评估器闭环 + 标准维护。

---

# 第一章 · 设计工程（可控的高质量生成）

核心：**把一项设计任务「从一句话到一版原型」的黑盒，拆成一条可在每个环节注入能力的链路。**

## 1.1 Design I/O（打开黑盒：从需求到原型）

**核心概念：黑盒 → 链路。** 输入是设计能力（对功能边界、业务语义、组件使用、视觉工艺、验收标准的判断），输出是符合规范的界面产物。中间是一组可被调用、检查、回流的接口。

**主链路（5 步）**：`Prompt → ① 理解/规划 → ② 搭骨架 → ③ 填充 → ④ 细化 → Prototype → 评估`

- 规划：定义功能为谁服务、覆盖哪些场景、哪些状态必须存在。
- 搭骨架：信息以什么空间结构铺开。
- 填充：内容映射到具体组件与业务语义。
- 细化：补齐交互状态、边界反馈、视觉工艺。
- 评估：对照标准检查，决定达标还是回流。

> 环节顺序不是随意的：上游偏差会沿链路放大，**约束最好尽早进入、每步持续检查**，而非末端补救。

**两条贯穿支线：**
- **token 注入**：颜色、间距、字号等约束贯穿「搭骨架→填充→细化」，是一条侧轨。一致性 ≠ 某一步做对，而是每一步都不破坏既有约束。
- **critique 回流**：评估不达标时，带着**具体问题**退回规划或相关环节，而非从头再来。（自我修正的早期形态）

**环节即接口（代价最小化）**：解决问题要能定位到具体环节，而不是在最外层反复改 prompt。

| 环节 | 进入这一步的能力 | 它约束什么 |
|---|---|---|
| 规划 | spec.md（交互规格） | 为谁做、覆盖哪些状态、什么算验收 |
| 搭骨架 | template / design.md | 骨架、密度、颜色、间距怎么取值 |
| 填充 | components / domain.md | 能用哪些组件、领域状态和数据怎么表达 |
| 细化 | craft.md / design.md | 动效、工艺细节、不显套路 |
| 评估 | evaluator | 按维度打分，达标 or 回流 |

## 1.2 设计声明与执行契约

**两类能力，对应两种失败：**
- **设计声明** —— 定义「什么样的设计是好的」（目标函数 / 方向）。
- **执行契约** —— 定义「怎么把它做出来」（求解过程 / 路径）。

| | 设计声明 | 执行契约 |
|---|---|---|
| 回答问题 | 什么样的设计是好的 | 怎么把它做出来 |
| 来源 | 生成结果反复错在同一类判断上 | 标准写了，但链路里没人调用 |
| 典型内容 | spec、domain、craft、design.md、components、template | skill、evaluator |
| 缺失后果 | 产物能跑但判断失准 | 标准很多但进不了流程 |

「声明管方向，契约管路径。二者互补，不是并列清单。」

### 六份设计声明（都回答：什么算对）

| 生成里暴露的问题 | 沉淀成的声明 | 它约束什么 |
|---|---|---|
| 主流程能跑，空态/错误态/权限态消失 | `spec.md` | 功能定义、状态流、边界条件、验收标准 |
| 页面像通用 SaaS，不像云安全/数据库/控制台 | `domain.md` | 领域语义、风险编码、业务操作边界 |
| 功能完整，但一眼是 AI 模板 | `craft.md` | 排版、层级、动效、材质等通用工艺 |
| 色值/字号/圆角/动效散落在代码里 | `design.md` | token、视觉语义、状态派生、系统缺口 |
| 组件看起来像，但语义用错 | `components` | 组件可用范围与语义边界 |
| 页面骨架从零猜，场景结构走偏 | `template` | 页面骨架、app shell、场景结构起点 |

**spec.md —— 功能定义声明（六个层次，抽象→具体，本质是一张完整性检查表）：**
```
L1 定位与意图   一句话定义、目标用户、场景清单、以及「非目标」
L2 信息架构     空间区域划分、内容按什么规则生长
L3 核心链路     走通功能要经过哪些状态、状态怎么流转
L4 组件功能细节 每个组件具体怎么表现
L5 边界条件     空、加载、错误、缺权限怎么办
L6 验收标准     满足哪些条件才算做对
```
- **L1 行为边界声明（三档自主权）**：始终（如自动保存草稿）／询问后（如发送数据到第三方）／永不（如重定向到可疑链接）。缺它 → Agent 或过度殷勤（到处「你确定吗」），或在敏感操作上擅自行动。
- **L5 加载态分档**：`<300ms` 不展示（人感受不到）／`300ms–2s` 骨架屏／`>2s` Loader+进度说明／`>10s` 超时提示+重试。**不是所有等待都需要安抚**。
- 缺 spec 的产物 =「能演示的代码」，而非「有边界、能降级、能恢复的功能」。

**domain.md —— 领域语义**：把业务数据和状态正确编码成视觉。O-insight 为例：字体栈必须显式 `SF Pro Display / PingFang SC`，禁回退宋体；告警色必须用语义色、分类色板按序使用。**缺它 → 套「换个品类也成立」的通用皮 + 系统割裂**（同一个用户在产品 A 见红=错误，产品 B 见红=最高热度，不再信任任何颜色）。

**craft.md —— 通用工艺（防 AI 味）**：不过分绑定业务的设计功底。点名常见 AI 痕迹：
- 字体：默认禁用被 AI 滥用的 serif；换项目须换字体组。
- 版式：机械化预检——数 section 顶部 uppercase eyebrow 标签数，超过 section 总数 1/3 直接 FAIL（九个都有 eyebrow 是模板，三个才是故意）。
- 动效：**每个动画都要被动机驱动**（解释层级/反馈/状态变化；「看起来很酷」不允许）。「三个有意义的动画，好过三十个无意义的闪烁。」

**design.md —— 视觉契约（单一事实源，可插拔）**：
- 绝大部分层（色彩/字体/间距/动效）通用、可继承；只有**领域语义层**换产品时整体替换（把业务对象映射到视觉编码，只换词表，模式复用）。「换产品只改三件事、其余继承」。
- **范式：所有视觉值走 `var(--*)`，禁止字面量。** 代码里不允许 `#fff`/`13px`/`200ms`；状态变体不新造 token，按公式从基础值派生：
```
hover:     color-mix(in oklch, var(--primary), var(--background) 8%)
disabled:  opacity 0.4
focus:     outline 2px solid var(--ring)  (不可移除)
```
- 好处：改一处 base，派生值全部联动。「合法地失败」——token 没覆盖时按严重度记 `gaps.log`；无可用替代就拒绝生成该部分、请人补 token，而非默默写字面量。
- 「坏味道」判据（与 evaluator 同源）：**「土气测试」**——把为某产品做的插画放到卖咖啡页面，若照样成立，说明是套通用「高级皮」，直接压分。

**components —— 组件注册表**：登记 shadcn 与自有库组件及用法边界、易混淆组件对、同名不同结构组件清单。缺它 → 凭印象选组件，相似但语义不同被用错。

### 三份执行契约（都回答：怎么做）
- **skill**：把一项能力封装成可被调度的单元。
- **template**：预定义布局与 app shell，从验证过的结构起点出发，而非每次空白。
- **evaluator**：把 design.md 的「坏味道」判据抽象成可打分的标尺。

**为什么两类都需要**：声明=目标函数，契约=求解过程。少了声明不知好坏；少了契约无法落地。配齐才是一套完整能力。

## 1.3 Skill：能力的封装与调度（实操）

**现实问题**：知识写下来 ≠ 会被用上。Agent 不知道它存在、不知道何时该读，就形同不存在。

**封装（一个 skill 的 4 部分）**：
1. **触发条件**（解决「何时该用」）：写在 description，列出触发信号。把调用时机也封装进去。
2. **能力主体**（解决「怎么做」）：固话一套原本靠经验的工作流（判断步骤）。
3. **分层引用**（解决「细节太多怎么办」）：主文件讲流程，庞大细节放 references 按需读取（如 30 个 cloudai 模版决策表）。按需加载 = 控制信息进入视野的时机与量。
4. **沉淀的坑**（解决「别再犯第二次」，最「贵」的部分）：原则 + 已知陷阱，每一条对应一次真实犯错，写进 skill 替所有人记住（如「不要 hardcode 颜色，用 token」）。

> 一个 skill = 一个触发时机 + 一套判断流程 + 一组按需调用的细节 + 一批沉淀的经验。

**调度（让 skill 在对的环节自动挂载）**：不是人记着步骤，而是让链路结构决定。

| 环节 | 挂载的 skill |
|---|---|
| 规划 | design-research / ux-spec / visual-spec |
| 搭骨架 | variant / cloudai-picker |
| 填充 | cloudai 组件库 |
| 细化 | cloudai-animation / craft |
| 评估 | check / review |

**调度 vs 手动调用**：手动调用是人记流程逐步喊；调度把流程固化进链路，让该出现的能力在该出现的地方自己出现。

# 第二章 · 动态交互（体验随意图被实时组织）

核心：用户不是带着「任务」来，而是带着「**意图**」来。界面不再预先画死，而是围绕上下文和任务状态实时组织。

## 2.1 从 UX 到 AX（Agent Experience）

- **UX**：帮用户把目标翻译成系统操作（导航、表单、反馈）。仍有效，尤其稳定的仪表盘、设置页、审批流。
- **执行鸿沟**：用户有目标，但不知道如何把目标转成系统动作——即使界面认真设计，用户仍卡住。
- **AX**：用户不必先懂页面结构，先表达**意图**，由 Agent 理解目标、补齐上下文、推进任务，再把过程与结果交回用户判断。
- **评估鸿沟**：执行鸿沟被压缩后，评估鸿沟更突出——用户没亲手做每步，更需要知道 Agent 做了什么、为什么、哪里不确定、能否撤销修正。

> 「UX 让路径更顺畅；AX 直接移除路径，把用户送到目标。」
> —— John Maeda, Design in Tech Report

**Agent Experience Loop**：用户表达意图 → Agent 理解并行动 → 界面承接协作节点 → 结果回到评估与控制。强调运行时的**持续往返**（非一次输入输出、非把聊天框放产品入口）。

**UX / AX 对照**：
- 设计对象：UX=用户如何操作界面；AX=用户如何委托、验证、修正 Agent 行动。
- 主要挑战：UX=降低认知与操作成本；AX=压缩执行鸿沟，处理放大的评估鸿沟。
- 界面职责：UX=呈现入口/路径/控件/反馈；AX=承接意图表达、过程协作、证据解释、结果评估。
- 典型形态：UX=页面/菜单/表单/按钮；AX=输入入口、动态交互卡片、生成产物。

**关键原则：过程透明度并非越高越好。** Agent 产生大量中间信息，全平铺会变成新的信息负担。应根据任务阶段、风险等级、决策需要，**动态调节界面暴露的信息层级**（参考 ACM CSCW 2025 论文）。

**设计前自检问题**：用户真的要完成什么目标（而非他说了什么）？哪些信息已明确、哪些要澄清？哪些步骤 Agent 可自动、哪些必须等确认？当前阶段该暴露多少信息层级？

## 2.2 GenUI：新的 Interface（有边界的灵活性）

- **GenUI（Generative UI）**：不是让模型任意生成页面，而是让**界面参与 Agent 系统的运行**——根据意图、上下文、任务状态，动态组织屏幕上该出现的内容、结构和判断点。
- 出现在不同位置：对话流、工作区、原生界面、生成后结果产物。判断标准一致：能否在运行时把任务状态转成可理解、可操作、可评估的界面。
- **边界要清楚**：只在任务路径、判断依据、用户决策点变化的地方引入 GenUI；稳定页面（仪表盘/设置页/审批流/长期 IA）不必为「生成」而重新生成。
- **两个判断维度**：表达自由度 vs 产品控制权。**并非越自由越好**。
- **受控生成（推荐路径）**：Agent 输出结构化意图/界面描述，客户端用组件目录、渲染规则、交互约束来组织界面 → 保留运行时组织能力，又让产品控制视觉质量、交互边界、安全风险。
- **引入前自检**：任务路径/声明结构是否随上下文变化？用户是否需过程判断、确认、修正？结构化界面是否比长文本更好懂？能否被组件目录和规则约束？

## 2.3 A2UI：对话 Loop 中的动态机制

- **A2UI（Agent to UI）**：GenUI 的一种实现机制——Agent 用**结构化方式声明界面意图**，客户端用受控组件、设计系统、交互规则完成渲染。**不是**模型自由写 HTML/CSS/组件代码。
- **本质是 Agent 与客户端的契约**：把「要表达什么」和「如何渲染」分开——Agent 参与界面组织，但不接管界面实现。**契约的作用是定义边界。**
- **契约调动的四类资源**：
  1. 业务数据（指标/表字段/实例状态/SQL 计划/生成资产/报告）
  2. 工作流（任务状态、下一步动作、Agent 是否暂停）
  3. 组件（客户端允许渲染的 UI 模板）
  4. 交互规则（决策策略、超时策略、校验、风险确认、动作分发）

**A2UI 消息结构（简化示意）**：
```json
{
  "intent": "confirm",
  "status": "pending",
  "title": "确认是否继续分析",
  "context": { "object": "业务对象/object-id", "time_range": "最近 24 小时", "finding": "发现 3 个异常项" },
  "content": { "type": "options", "items": [
    { "id": "item_1", "label": "选项 A", "description": "影响范围最高/建议优先分析" },
    { "id": "item_2", "label": "选项 B", "description": "调用次数上升/需继续观察" }
  ]},
  "actions": [ { "id": "analyze_selected", "label": "分析选中项", "primary": true }, { "id": "view_all", "label": "查看全部" } ],
  "behavior": { "requires_user_decision": true, "blocks_agent_execution": true }
}
```
重点不是字段名，是分工：Agent 不决定按钮长什么样、卡片颜色、图表排版；只说明任务状态、展示数据、可行动作、是否阻塞执行。客户端据此选组件、按设计系统渲染。

**FlexCard（CloudAI 落地）**：不让 Agent 描述视觉细节，而是描述意图、内容、动作、行为约束。渲染层映射到组件/token/无障碍/降级状态。用户点击/选择后，客户端带上下文把动作传回 Agent → 界面不只展示结果，也**把用户判断重新写回任务上下文**。

## 2.4 案例：OmniBox → FlexCard → GenReport

**三段式链路**（Agentic 云产品）：OmniBox 承接意图表达，FlexCard 承接过程协作，GenReport 承接结果评估。

- **OmniBox（意图输入）**：把自然语言、数据范围、知识库、指标对象、历史上下文放进同一入口。做「意图结构化」：识别任务对象、分析维度、时间范围、权限边界、业务线索 → 转成 Agent 可推理的上下文。
- **FlexCard（过程协作）**：承接中间判断（如「按产业/品牌/门店拆解选哪个」；高权限 SQL 查询 / 数据库性能影响需先授权）。把「不确定的是什么/可选路径/会访问什么数据或产生什么风险」放同一张结构化卡片。
- **GenReport（结果评估）**：结果复杂的 Artifacts 产物。它不是固定模板，也不是 A2UI 卡片放大版，仍属 GenUI（结构/重点/证据随目标与数据状态变化），但被**声明式规则约束**（哪些指标必须出现、图表如何绑数据、洞察引用哪些证据、风险/建议如何落组件）。

**一份可用 GenReport 回答 4 问**：关键指标表现如何？哪些结构性问题/风险值得关注？证据来自哪些图表/明细/对比？建议动作和后续跟踪方式是什么？

> 不是所有页面都要生成：**要识别哪些时刻会因意图/上下文/数据/决策变化而需要动态界面。**
> Agent 至此具备两件能力：①按规则组织界面（第一章）②在运行时接住任务过程（第二章）。下一章解决「越做越好且不靠人盯」。

# 第三章 · 自我进化（从人工指正到评审运行时）

核心：自我进化 ≠ AI 自夸变好。而是把「稳定判断」变成一套可运行的**评审循环**，不断沉淀、回流、校准。

## 3.1 人工指正的尽头

- **现状问题**：质量取决于看几遍、能否稳定说清「为什么不对」。且很多指正是重复的——「第一屏看不出主任务」「CTA 与真实目标不一致」「卡片节奏太平均」「像通用模板」「指标缺来源/时间窗」「按钮点了没反馈」。**这些不是灵感，是稳定判断。稳定判断应该被沉淀。**
- **两个基本角色**：
  - **生成器**：把输入变成原型。输入 = 自然语言需求 + Spec/Skills/component.md/design.md 等设计资产。「提出第一版方案的人」。
  - **评估器（Evaluator）**：判断原型能否进入下一步。不生成方案、不做主观打分，像**审稿人**：只看当前原型+评审标准，判断产品意图、表达、系统工艺、内容语气、交互是否就绪。

**Evaluator 基础闭环（4 环节）**：
1. 生成器基于设计输入产出一版原型。
2. 评估器按评审维度判断是否达标。
3. 达标 → 进入最终设计输出。
4. 不达标 → 输出**优化指令**（说明哪些判断没成立、证据在哪、下轮先改什么），回到生成器。

- 优化指令不是「再优化一下」，而要定位：第一屏看不出主任务 → 回到 Product Intent；组件状态不稳 → 回到 System Craft；关键动作无反馈 → 回到 Interaction Readiness。
- 工程机制：原型的 Web artifact → **Prepare**（打开页面、采集截图、DOM/CSS QA、click smoke）→ **评估**（按 rubric + 权重输出结构化判断）→ **Finalize**（重算分数、处理 blocking findings、生成报告 + return plan）。

**人工指正 / 评审运行时对照**：
- 判断来源：人的经验状态 vs 任务/截图/QA/rubric/权重。
- 问题表达：「再精致一点」vs 维度、subcheck、证据、扣分原因。
- 迭代输入：人转述 vs return plan 直接回流。
- 可复查性：换人标准漂移 vs 报告/JSON/截图/QA 可追溯。

**这不是取消人，是人的位置上移**：人不再每轮循环纠错，而进入上游修订 framework/prompt/schema/harness policy，把稳定判断写成运行时能执行的契约。**分数只是外显结果，真正重要的是证据链与回流路径。**（无证据链→AI 把完整度误当质量；无回流路径→评估只是事后报告。）

## 3.2 评估标准：页面类型与六维度模型

**两个前置问题**：这一版原型属于什么页面？这类页面应按什么目标评估？（解决「用错尺子」）

**先判断页面类型（三类任务）**：

| 页面类型 | 所属任务 | 主任务 | 典型失败方式 |
|---|---|---|---|
| Brand Landing Page | 转化型 | 把注意力转成兴趣与信任 | 通用模板、品牌记忆弱、承诺含混 |
| Product Console | 任务型 | 帮用户安全完成操作任务 | 主任务不清、状态断裂、信息密而无用 |
| Conversational Interface | 任务型 | 帮用户通过对话提问、判断、恢复 | 轮次状态不清、回答无依据、缺少恢复 |
| Data Dashboard | 判断型 | 帮用户判断状态并诊断变化 | 装饰大于含义、指标层级弱 |
| Content/Documentation | 判断型 | 帮用户找到并应用知识 | 难扫描、结构弱、声明无证据 |

无明确任务时，Prepare 从 Web artifact 的 title/h1/导航/链接/文案/图片/结构**推断临时目标**（标记 `inferred_from_artifact`）。

**六维度模型**（从三类真实业务关注拆出，避免把不同问题混在「好不好看」）：

| 维度 | 中文名 | 评审关注 |
|---|---|---|
| Product Intent | 产品意图 | 价值主张、目标用户、主任务、内容语气、CTA 是否匹配真实目标 |
| Trust & Domain Fit | 业务可信 | 领域术语、数据声明、风险权限、合规、AI 置信和证据是否可信 |
| Information Architecture | 信息架构 | 层级、分组、导航顺序、密度、节奏是否服务扫描和决策 |
| Interaction Readiness | 交互就绪 | 控件可理解、动作有反馈、关键路径可完成和恢复 |
| System Craft | 系统工艺 | 字体、间距、圆角、阴影、组件、状态、桌面布局是否像一套系统 |
| Visual & Brand Expression | 视觉品牌 | 色彩、字重、图像、动效是否形成适合品类的品牌表达 |

三层映射：业务语义层→(Product Intent, Trust & Domain Fit)；用户任务层→(Information Architecture, Interaction Readiness)；界面实现层→(System Craft, Visual & Brand Expression)。

**权重随页面类型变化**（同一组维度，重心不同；不把页面压成同一种模板，也不失共同语言）：

| 维度 | Brand Landing | Product Console | Conversational | Data Dashboard | Content/Doc |
|---|---:|---:|---:|---:|---:|
| Visual & Brand Expression | 25% | 8% | 8% | 8% | 8% |
| Product Intent | 20% | 22% | 18% | 18% | 18% |
| Information Architecture | 18% | 22% | 16% | 24% | 28% |
| System Craft | 15% | 14% | 12% | 16% | 14% |
| Trust & Domain Fit | 12% | 18% | 22% | 22% | 22% |
| Interaction Readiness | 10% | 16% | 24% | 12% | 10% |

**Subcheck 让维度可追账**（0–2 分）：
- 2 pass：基本满足，仅需轻微修整。
- 1 partial：部分满足，弱点已影响质量。
- 0 fail / critical_fail：不满足；critical_fail 进入阻断判断。
```
dimension_score = sum(subcheck.score) / sum(subcheck.max_score) * 10
```
从印象打分 → 证据打分：必须先检查每个 subcheck、记录证据/扣分原因/建议，再向上聚合。「分数要能反推」。

## 3.3 证据链：浏览器、截图与检查项

- **Evaluator ≠「让模型看段 HTML 再打分」**，而是一套**多模态证据运行时**：先收集证据，再交给评审模型，最后由运行时重算分数、处理阻断、生成报告。
- 「像人一样评估」= 先获得接近真实评审者的证据条件：页面真被打开、画面真被截图、控件真被点击、结构状态真被检查、语义放回目标核对。**Evaluator 面对的是交付物，不是生成器的意图。**

**生产入口**：`Evaluator/harness/design_review_cli.mjs`（读取任务/产物 → 解析页面目标 → 启动 Chromium → 打开页面 → 写入评估输入）。

**四层证据**：
| 证据层 | 内容 |
|---|---|
| DOM/CSS QA | 横向溢出、文字裁切、低对比度、fixed 溢出、小点击目标、交互元素缺名称、图片损坏 |
| Page Profile | section、图片、链接、真实路径、占位链接、导航文案、headline、CTA、可点击目标 |
| Click Smoke | 点击可见目标后是否有 console error、page error、broken image、dialog、或无反馈 |
| Screenshot | 桌面端截图 + full-page 截图，供 visual review 与报告引用 |

- 默认视口桌面端 `1440x1000`；**审查看不见的不扣分**（desktop-only 边界）。运行时**阻断外部字体依赖**减少非确定性（同一原型每次字体不同 → 截图判断成偶然）。
- **浏览器 QA 是事实层，不是评分层**：能抓溢出/断图/太小/点击报错，不能判品牌记忆、链路安心感。无 critical QA 仍可能很弱（首屏无读点/模块像模板/图表无诊断/点击无状态）。**浏览器把问题变事实，模型解释影响，运行时收束分数。三者不可互相替代。**

**截图补上 DOM 看不到的问题**。当 DOM/CSS 检查与截图冲突时，**截图证据优先**（用户看到的是画面，不是 DOM）。五类截图判断：
| 检查项 | 关注点 |
|---|---|
| text_readability | 文字是否真实可读 |
| visual_hierarchy | 主次与阅读路径是否清楚 |
| composition_risk | 构图是否遮挡信息、制造空洞、破坏节奏 |
| brand_tone_fit | 视觉语气是否匹配品牌与品类 |
| motion_purpose | 动效/视觉效果是否服务页面目标 |

**检查项落回评分模型**（`evaluation-output.schema.json` 结构约束）：
- 每个维度：`dimension`、`score`、`subchecks`、`evidence`、`why_not_higher`、`recommendation`。
- 每个检查项：`id`、`label`、`score`、`max_score`、`verdict`、`evidence`、`deduction_reason`、`recommendation`。
- 让截图问题进入对应维度检查项、点击问题进入 Interaction Readiness 并判断是否阻断。

**把判断收束为可追溯结果**：模型总分只是建议；**最终分数由运行时按六维度、检查项分、页面类型权重重算**。分工：模型评审（输入任务/截图/QA/标准/输出结构，责任=判断质量/写证据/给建议）vs 运行时裁决（输入模型结果/权重/评审模式，责任=重算分数/处理阻断/生成报告）。输出：`evaluation-output.json` → `resolved-evaluation.json` + `report.html`。

## 3.4 交付闸门：从分数到放行判断

- **为什么不能只输出分数**：平均分会掩盖致命问题（视觉完整但主任务不清；控制台专业但按钮/详情不响应；对话界面漂亮但回答没来源/置信/恢复）。**闸门回答的不是「几分」，而是「能不能进入下一步」。** 三类信息收束：结构化评分 + 成熟度阶段 + 阻断问题。

**三种评审模式（产品成熟度）**：
| 评审模式 | 阶段 | 阈值 | 交互与集成策略 |
|---|---|---:|---|
| 过程稿评审 `vibe_draft` | 方向探索 | 7.5 | 先看方向/意图/IA/品牌/工艺；后端、路由、占位链接多为提示 |
| 原型评审 `prototype` | 路径演示 | 8.0 | 不要求真实后端，但主路径需可见模拟状态；交互问题影响通过 |
| 上线门禁 `release_gate` | 交付验收 | 8.0 | 要求生产化路径/导航/数据/关键状态；占位路径可能阻断 |

评审模式**不改变评分模型**（六维分数+检查项分+页面类型权重不变），只改变**放行策略**（提示 vs 阻断）。同一问题在不同阶段严重度不同。

**阻断问题（不能被平均分摊薄的失败）**：`unclear_primary_task`、`critical_rendering_failure`、`hero_primary_copy_unreadable`、`primary_visual_blocks_information`、`wrong_domain_logic`、`broken_key_task_path`、`operation_flow_has_dead_end`、`disconnected_controls_or_states`、`broken_conversation_flow`、`untrustworthy_ai_response`、`brand_tone_mismatch`、`placeholder_or_missing_conversion_paths`、`generic_template_output`、`inconsistent_design_system`、`subcheck_evidence_missing`、`screenshot_review_missing`、`critical_subcheck_failure`。

**优化指令 = 压缩**：不产出长愿望清单，只挑最影响通过的少数问题，说明证据位置/影响维度/下一轮方向。例：
> ❌ 继续优化视觉、增强交互、丰富内容。
> ✅ 第一屏价值主张被产品图遮挡，影响 Product Intent 与 Visual & Brand；先调标题层级/图文关系/CTA 位置。主 CTA 点击无反馈，prototype 模式影响 Interaction Readiness；下轮需弹窗/抽屉/局部状态/模拟路径。

**停止规则保护循环**（能停也是能力）：达阈值且无阻断 → 通过；达最大轮数 → 停；连续多轮标准差小且最佳分提升有限 → 平台期；修订导致分数明显下降 → 返回之前的更好版本。自我进化不是无限迭代，而是证据显示已通过/平台期/走偏时做**可解释的停止判断**。

## 3.5 工程化与标准维护

**运行时三件事**：①知道能看什么、不能看什么；②把评审转成团队可读可复盘可行动的**报告**；③允许标准在运行时之外持续校准（不把一次 prompt 写成永恒规则）。

**隔离系统保护评审对象**：生成器与评估器必须分离，避免「意图污染」。
- **可读（外显材料）**：任务目标、页面原型、运行截图、浏览器检查结果、交互路径、六维度评分模型、页面类型权重、上一轮评估结果。
- **不可读（内部材料）**：生成器提示词、隐藏规划、私有推理、作者事后解释、无关项目历史。
- 关键：生成器计划了完整链路但页面只有占位按钮 → 按占位按钮处理；说「后续接真实数据」但当前无路径/状态/反馈 → 仍记为证据。**评审看的是稿件，不是作者脑中的稿件。**

**报告契约（五层信息，进入协作）**：
1. 放行结论：最终分数、阈值、评审模式、通过/退回原因。
2. 六维度评分：六维正式分数。
3. 证据解释：截图/结构/点击路径/运行健康/浏览器检查如何支撑判断。
4. 阻断问题：哪些不能被平均分抹平、为何影响放行。
5. 优化指令：下轮最应解决的少数问题 + 证据位置 + 影响维度。
- **刻意把「评分」与「证据解释」分开**；报告**中文优先**（正文说「过程稿评审/原型评审/上线门禁」，不暴露内部枚举字段）。白皮书面向构建思想，不是接口说明。

**标准维护在运行时之外**（通过案例复盘持续校准）——几类样本：
- 好案例（保护别过严）・坏案例（检查阻断识别）・混合案例（局部出色但主路径失败→校准平均分与放行关系）・边界案例（接近阈值→看权重/检查项稳定性）・品类案例（美妆/金融/云产品/文档/控制台→校准同维度在不同品类的表现）。
- **每次标准更新答 4 问**：是否减少误放行？是否造成新误退回？是否过度惩罚某类页面？是否只修好一个样本却伤害其他样本？
- 「标准不是一次写完的。**标准是在案例里长出来的。**」

**完整闭环**：生成器（承接意图/目标/页面类型/组件约束/交互目标/视觉表达→产原型）→ 评估器（打开页面/截图/读结构/查路径/触发关键操作/记运行状态 → 六维评分 → 交付闸门结合评审模式+阻断做放行）→ 通过则进入下一步；未通过则转优化指令回流生成器。运行时之外，团队用真实案例维护页面类型/维度定义/检查项/放行策略。
- **AI 不是多跑几轮就变好。它需要一套会看、会判、会回流、会校准的系统。**
- 评价闭环的本质：生成器提出可能性，评估器让可能性接受证据检验，标准维护让检验方法越来越接近真实业务判断。

# 结语：把「什么是好」讲清楚

三章不是三套分散能力，而是一条连续的工作方式：
- **第一章**解决生成前可控性：把功能边界、领域语义、组件规则、视觉工艺、验收标准写成 Agent 能读的声明与契约。
- **第二章**解决运行中适配：界面围绕任务状态、上下文、下一步动作被实时组织。
- **第三章**解决生成后改进：用 evaluator 把稳定判断变成可执行的检查与回流，让每一版留下经验。

**根本问题：设计专业如何进入系统。**
- 过去判断停在设计师脑里（评审意见、口头提醒、Figma 标注、返工形式）。人能理解，Agent 不能稳定继承。
- 解法不是让 AI 凭空理解设计，而是**把判断拆开、写清、放进链路**：
  - `spec.md` 定义功能怎样才算成立，`domain.md` 定义业务语义，`craft.md` 约束工艺质量，`design.md` 管视觉事实源，components 和 template 限定可用边界，skill 负责调度，evaluator 负责检查与回流。
- 合起来，「好设计」从经验判断 → 可被引用、被执行、可追责的**系统能力**。

**AI 时代设计师最重要的位置**：不是退到旁边看模型生成，也不是把专业压成更聪明的 prompt，而是**把判断本身交给系统**——什么值得突出、什么必须克制、什么状态不能缺席、什么表达会伤害信任、什么样的结果才算完成。

- 这不会让设计机械化，反而让最难复制的部分（判断、取舍、尺度、语气、信任感）更清楚。模型生成更多方案、工具缩短更多路径，但这些仍需要人定义。没有人的判断，系统只会更快地产生平均答案。
- 「真正值得投入的，不是让 AI 看起来更像设计师，而是让它持续靠近我们定义过的好。**定义「好」的人，仍然决定设计的边界。**」

# 附录：设计提示词词典（12 类 188 词节选精华）

把「高级」「克制」这类抽象词翻译成 Agent 能执行的表达规则。以下为高频实操重点，完整 188 词见站点 Lexicon 板块。

**01 · Typography 排版**
- Kerning 字偶间距 / Tracking 字间距（大写标签几乎都需加宽）/ Leading 行高（太紧窒息，太松不成段）
- Tabular nums 等宽数字（价格/统计/刷新数据必用）/ Type scale 字号阶 / Clamp 流体字号
- Widow 孤字（text-wrap: balance）/ Orphan 孤行 / Font stack 字体栈 / Line length 行宽≈65 字符
- Text overflow 文本溢出（用单个 unicode 字符截断、不切词）

**02 · Color 色彩**
- sRGB / P3 广色域 / OKLCH 感知均匀色彩空间（同 lightness 感觉一样亮）
- Semantic token 语义 token（用用途命名而非 hex）/ Contrast ratio 对比度（正文 4.5:1、大字/UI 3:1）
- Tinted neutral 带色调中性灰（纯 #808080 像占位符）/ Chroma 彩度（浅色降 chroma 别降 opacity）
- Gradient 渐变（OKLCH 里建避免中点发灰）/ Dark mode（最亮表面应在层级最上）

**03 · Iconography 图标**
- Stroke weight 描边粗细（随尺寸缩放）/ Optical centre 视觉中心（播放键数学居中会偏左）
- Filled vs outlined（filled 常表选中）/ Meaning collision 语义冲突（同一图标别表两种动作）
- Breathing room 呼吸间距（6-8px 起步）/ Unified weight 统一权重（细描边图标配粗体字像来自不同产品）

**04 · Layout 布局**
- Border radius 圆角（内层 = 外层 − padding）/ Gap 间隙（设父级）/ Negative space 负空间
- Layout shift 布局抖动（预留空间+等高回退字体）/ Sticky（父级 overflow:hidden 会破坏它）
- Breakpoint（设在内容真正断裂处，非假设设备宽）/ Grid（12 列惯例，简单布局 8 列更好）

**05 · Interaction 交互**
- Affordance 可供性 / Hover/Focus/Active/Disabled 各态 / Touch target 触控目标最小 44×44px
- Optimistic update 乐观更新（失败需回滚）/ Debounce 防抖（搜索 300ms）/ Copy to clipboard 需可见确认
- Skip link 跳过链接（键盘用户必需）

**06 · Motion 动效**
- Easing（ease-out 入场、ease-in 离场、ease-in-out 屏内位移）
- Stagger 错峰（列表 40ms 依次）/ Duration（hover≈150ms，400ms 像思考）
- Transition property（只 opacity+transform）/ Reduced motion 减弱动效（明显位移都要检查）
- Choreography 编排（协调多元素，让眼睛知道看哪）/ Motion as feedback 动效即反馈

**07 · Accessibility 无障碍**
- WCAG（AA：正文 4.5:1、大字/UI 3:1）/ APCA 感知对比 / Tab order / Focus trap
- aria-label（描述动作非元素类型）/ DOM order（读屏器跟 DOM 走）/ Semantic HTML（用 button 非 div 扮）
- Color-only state 仅颜色状态（色盲用户不可见，须配图标/文字）

**08 · Information Architecture 信息架构**
- Progressive disclosure 渐进披露（反面是一页堆所有）/ Mental model 心智模型 / Hierarchy 层级
- Empty state（解释为何并给下一步，「无数据」终结旅程）/ Error state（说清错误+具体恢复方式）
- Confirmation dialog（说会失去什么、危险与安全动作视觉拉开）/ Wayfinding 寻路 / Depth 层级深度（3 层上限）
- Search as escape hatch（可浏览却高搜索量 = IA 需改进信号）

**09 · Copywriting 文案**
- Microcopy 微文案 / CTA（"Save changes" 比 "Submit" 可信，别道歉）/ Error message（"邮箱须含 @" 胜过 "Invalid input"）
- Placeholder 不能替代 label / Sentence case 句首大写（标题第一个词才大写）
- Front-loading 前置关键词 / Inline error 行内错误 / Destructive language 破坏性用词要明确（别用 clear/reset 软化）
- Scannability 可扫读 / Truncation strategy（词边界截优于切字符）

**10 · Tools 工具**
- Design system / Source of truth（越来越多 = 代码库本身）/ Variables / Tokens / Visual language
- Prototype（保真度匹配要回答的问题）/ Handoff（准确规格+共享 token+可答疑）/ Redline 标注
- OG 元数据（分享预览的常被忽视的第一印象）

**11 · Analysis 分析**
- A/B test / Heatmap / Session recording / Funnel / Conversion / Bounce rate / Retention / Churn / NPS / Scroll depth（多数用户到不了底）

**12 · Components 组件**
- Button（一屏不超一个 primary）/ Input（上方持久 label，不只占位符）/ Select（自定义小心键盘焦点）
- Modal（焦点必须困在内）/ Popover（可含交互）vs Tooltip（不能含交互内容）
- Toast（时长反映阅读时间非固定 2s）/ **Badge（附着、信息性）vs Tag（独立、可移除）——两者不同**
- Accordion（FAQ，不替代需横向对比的 tabs）/ Tabs（同空间切相关视图）/ Stepper（提前显示所有步骤设期望）
- Data table（数字右对齐+tabular-nums，正确对齐胜过斑马纹）/ Combobox / Command menu
- Skeleton（列表/页加载优于 spinner）/ Spinner（不确定时长的短等待）
- Separator（常在更好的间距能解决时被过度使用）/ Empty state（"无结果" 什么都没告诉用户）

## 附：日常设计任务速查（关键判据清单）

**评审展开前先建立尺子**：
1. 判断页面类型（转化/任务/判断 → Brand Landing / Product Console / Conversational / Data Dashboard / Content-Doc），选对应权重表。
2. 用六维度模型逐维评审，每个维度拆 subcheck、记录 evidence / deduction_reason / recommendation，聚合出分（可反推）。
3. 结合评审模式（process draft 7.5 / prototype 8.0 / release gate 8.0）+ 阻断问题做放行判断（分数 vs 能否通过是两件事）。
4. 通过 → 输出；未通过 → 输出压缩的优化指令（问题 + 证据位置 + 影响维度 + 下轮方向），回流生成器。
5. 运行时之外：用好/坏/混合/边界/品类案例持续校准标准。

**回流索引（看到问题 → 回到哪里）**：
- 主流程能跑但空态/失败/权限态缺失 → `spec.md`
- 页面不像这个业务 → `domain.md`
- 页面有 AI 味 → `craft.md`
- 色值/字号/动效时长写散了 → `design.md`
- Badge/Tag、Dialog/Drawer 混用 → `components`
- 页面结构像卡片墙不像看板 → `template`
- 评估说不清哪里错 → `evaluator`

**设计声明是六份 + 执行契约是两份**：
- 声明：spec.md · domain.md · craft.md · design.md · components · template
- 契约：skill · evaluator

**关键立场（贯穿全书）**：
- 对象先是信息如何被组织、暴露、验证，界面只是最后可见结果。
- 约束尽早进入、每步持续检查，不做末端补救。
- 受控生成优于无限自由；透明度按阶段/风险/决策需要动态调节。
- 分数只是外显，证据链 + 回流路径才是价值。
- 标准在案例里长出来，定义「好」的人决定设计的边界。
